# Project Art avatar final-pass provider candidate materialization

This boundary admits the exact successful output of one governed avatar final-pass provider job into a persistent Artist Workspace.

It starts only after the existing provider-runtime bridge has produced:

```text
candidate-materialization-required
```

It ends with:

```text
one unapproved candidate PNG
one self-hashed materialization receipt
one self-hashed avatar frame-finisher request
```

It does not approve, promote, publish, deploy or activate the candidate.

## Why this boundary exists

The provider runtime stores generated bytes in the immutable `@evavo/art-artifacts` store. The avatar final-pass runtime outcome names the exact candidate artifact, evidence artifact and governed scratch path, but deliberately does not copy image bytes into the workspace.

This materializer closes that gap without weakening the review boundary.

It prevents a provider result from being treated as a finished sprite merely because generation succeeded.

## Required source chain

Every materialization revalidates the exact self-hashed chain:

```text
avatar provider runtime dispatch
→ avatar provider runtime binding
→ successful avatar provider runtime outcome
→ immutable candidate artifact
→ immutable provider evidence artifact
```

The dispatch, binding and outcome must agree on:

- Job and frame identity.
- Provider operation and continuity phase.
- Provider request input SHA-256.
- Normalized provider request ID and SHA-256.
- Compiled prompt SHA-256.
- Submission idempotency key.
- Candidate artifact ID.
- Evidence artifact ID.
- Candidate scratch path.
- Reviewed target path.
- Expected canvas.
- One-candidate scope.
- Native-alpha PNG requirement.
- Disabled provider fallback.
- All-false approval and activation authority.

A failed provider outcome, zero-candidate outcome, multi-candidate outcome or alpha-extraction-required outcome cannot enter this native-alpha materializer.

## Immutable artifact admission

The candidate artifact must pass `LocalArtifactStore.verify()` before and immediately before publication.

Its descriptor must remain:

```text
mediaType       image/png
storageClass    intermediate
artifactRole    provider-candidate
approvalState   unapproved
candidateIndex  1
finalDeliverable false
requiresMastering true
requiresBlockingQa true
```

The descriptor must bind the exact:

- Provider request ID.
- Candidate family.
- Asset ID.
- Continuity phase.
- Normalized request SHA-256.
- Compiled prompt SHA-256.
- Native-alpha background strategy.
- Required transparency target.

The provider evidence artifact must remain:

```text
mediaType     application/json
storageClass  evidence
artifactRole  provider-candidate-evidence
outcome       candidate-produced
```

Its immutable source-artifact set must include the exact candidate.

The evidence JSON must bind:

- The same provider request ID and request SHA-256.
- The same compiled prompt SHA-256.
- The exact normalized request object.
- One exact candidate artifact.
- One successful provider attempt.
- The adapter and model recorded by the runtime outcome.
- Eligible routing with fallback disabled.
- No provider call performed by the routing inspection.
- Native alpha with no deferred alpha extraction.

## Strict PNG admission

The candidate is decoded before workspace publication using Node built-ins only.

The validator checks:

- Exact PNG signature.
- Bounded file size.
- Bounded chunk count.
- Valid CRC for every chunk.
- `IHDR` first.
- Consecutive `IDAT` chunks.
- One empty `IEND` at the file end.
- No trailing bytes.
- No APNG `acTL`, `fcTL` or `fdAT` chunks.
- No unsupported critical chunk.
- Exact expected width and height.
- Eight-bit RGBA colour type.
- Standard compression and filter method.
- Non-interlaced output.
- Bounded inflate size.
- Valid row filters.
- At least one visible pixel.
- At least one transparent pixel.

The receipt also records:

- Visible and transparent pixel counts.
- Partial-alpha and opaque pixel counts.
- Hidden RGB beneath fully transparent pixels.
- Visible bounding box.
- Visible edge-contact count.
- Exact image byte length and SHA-256.

Hidden RGB is evidence for the frame finisher. It is not silently cleaned during materialization.

A fully opaque provider background is rejected rather than being represented as a transparent avatar frame.

## Create-only transaction

The materializer derives these three paths from the sealed candidate path:

```text
candidate-01.png
candidate-01.materialization.json
candidate-01.finisher-request.json
```

All three files share one governed directory.

Publication is:

1. Root-confined.
2. Symlink-rejecting.
3. Single-link constrained.
4. Private by default.
5. Staged in the destination directory.
6. Flushed before publication.
7. Linked into place create-only.
8. Rolled back if any member cannot be published.
9. Re-read and hash-verified after publication.

No existing file is overwritten.

A complete exact retry returns the existing verified bundle. A partial bundle fails closed and requires operator inspection rather than guessing which file is authoritative.

## Frame-finisher handoff

The materializer creates a hash-bound request for the permanent avatar frame finisher.

The request carries:

- Source commit.
- Session, character, job and frame identity.
- Candidate path and SHA-256.
- Candidate artifact and descriptor identity.
- Provider evidence artifact and descriptor identity.
- Runtime outcome SHA-256.
- Exact canvas and alpha evidence.
- Reviewed target path.
- Required finishing and review gates.

Its required sequence is:

```text
clear hidden RGB under transparent pixels
→ preserve canonical canvas and registration
→ run avatar frame finisher
→ inspect at native scale and in contact sheets
→ review hands, anatomy, face identity and continuity
→ rerun sequence and final-to-first loop closure
→ record a final reviewed frame SHA-256
```

The final reviewed SHA-256 remains mandatory before the frame can feed a dependent in-between or a runtime sequence.

## CLI

Build the artifact package first:

```powershell
pnpm --filter @evavo/art-artifacts build
```

Inspect capabilities:

```powershell
node scripts/avatar-final-pass-provider-candidate-cli.mjs capabilities
```

Materialize one exact candidate:

```powershell
node scripts/avatar-final-pass-provider-candidate-cli.mjs materialize `
  --dispatch C:\EVAVO\Evidencevatar-runtime-dispatch.json `
  --binding C:\EVAVO\Evidencevatar-runtime-binding.json `
  --outcome C:\EVAVO\Evidencevatar-runtime-outcome.json `
  --artifact-root C:\EVAVO\ArtArtifacts `
  --workspace-root C:\EVAVO\ArtWorkspaces\eva-final-pass `
  --actor-class agent `
  --actor-id evavo-avatar-finishing-agent `
  --authorization-evidence-sha256 <sha256> `
  --authorized-at 2026-08-13T00:00:00.000Z
```

The CLI never accepts image bytes, base64 content or an arbitrary destination path. The destination comes from the sealed runtime dispatch.

## Authority boundary

A successful receipt records technical authority only for:

```text
artifact read
provider evidence read
unapproved candidate materialization
materialization receipt persistence
frame-finisher request persistence
```

It grants no authority for:

```text
provider execution
alpha extraction
deterministic QA completion
creative review
candidate approval
candidate promotion
target repository mutation
Git mutation
deployment
publication
runtime activation
force push
```

Materialization is not artistic approval.

A candidate can still contain hand, finger, anatomy, face, registration, timing or continuity defects. Those defects remain the responsibility of the frame finisher and independent review stages.

## Validation

The focused suite covers:

- Exact successful materialization.
- Complete-bundle idempotent readback.
- Fully opaque background rejection.
- Fully transparent candidate rejection.
- PNG CRC rejection.
- APNG rejection.
- Canvas drift rejection.
- Approved-descriptor rejection.
- Provider-evidence substitution rejection.
- Deferred alpha-extraction rejection.
- Runtime-outcome hash tampering rejection.
- Partial-publication rejection.
- Last-moment artifact drift rejection.
- MCP capability and write-gate behavior.
- Separate record, artifact and workspace root confinement.
- No image-byte fields in the MCP contract.
